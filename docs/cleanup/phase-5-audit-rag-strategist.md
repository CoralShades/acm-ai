### F1 — E1-S14 contextual embeddings: intact, SF-clean

**Status: VERIFIED INTACT. Zero SF-field writes.**

- `save_records()` at `acm_extraction.py:2900` executes `acm_record.enriched_text = acm_record.get_enriched_embedding_text()` unconditionally for every saved record.
- `get_enriched_embedding_text()` at `acm.py:615` prepends `area_type` and `page_number` context to the base `get_embedding_text()` output. These are read-only concatenation of existing struct fields — no LLM call, no inference.
- `ACMEmbeddingService.embed_records()` at `acm_embedding_service.py:80-83` also calls `get_enriched_embedding_text()` for the re-embed API path.
- Fields written by S14: `enriched_text` (str), `embedding` (vector), `embedding_text` (str), `embedded_at` (datetime).
- Cross-check against `ITEM_SF_MAPPING` (confirmed by prior research in `rag-disposition-research.md`): **none of these four fields appear in the SF mapping**. S14 is fully chat/search-layer-only.
- Note on timing: `save_records()` only populates `enriched_text`. The actual embedding vector is generated by `ACMEmbeddingService` separately (via POST `/api/acm/re-embed` or post-extraction trigger). The `enriched_text` written during extraction is the correct input for that later embedding step.

## Strategic Verdict

**The RAG stack is correctly scoped. It is not over-engineered for current requirements.**

The project has two clearly separated concerns:

| Layer | Components | Rule | Status |
|---|---|---|---|
| **Extraction path** | LLM extraction → enum normalizer (Layer 1) → validation → SF export | Literal-only + deterministic mapping. No LLM inference over SF-bound fields. | Compliant post-5dc3ef30. |
| **Chat/search path** | contextual embeddings (S14) → vector index → hybrid search (E11-S2) → parent retrieval (E11-S1) | No rule against LLM-free retrieval enhancements | Fully intact, no violations. |

The only RAG component that violated the literal-only rule was E1-S15 Layer 2 (`_llm_correct_records()`). That is now dead code — disabled in 5dc3ef30, confirmed zero call sites.

**Retain**: E1-S14 (contextual embeddings), E1-S15 Layer 1 (synonym normalizer), E11-S1 (parent document retrieval), E11-S2 (hybrid search). All serve chat/search retrieval quality without touching the SF export path.

**Delete in E38-S2**: `_llm_correct_records()` function body + docstring reference in `acm_schemas.py:455`.

**Fix in E38-S2**: Remove `hygienist_recommendations @1@ $query` from `acm_hybrid_search_service.py:49` when that field is deleted from the domain.

A simpler retrieval path is NOT warranted. The retrieval components are used, tested at the integration level by the semantic search tool, and provide genuine chat-quality value. Removing them would degrade the user-facing Q&A capability with no SF-compliance benefit.
