2. Pipeline Architecture Audit
2.1 Current State: Monolithic Extraction
The current pipeline uses a single LLM call per building (via building_extraction.jinja prompt) that performs all extraction, interpretation, normalisation, and BAR-field mapping in one shot. While this works for Broadmeadows, it creates a fragile single point of failure: if the LLM misinterprets one aspect (e.g., sample results), it may cascade errors into related fields (friability, risk status).
[TABLE]
 | BMAD FINDING: SINGLE-AGENT BOTTLENECKThe extraction stage violates the BMAD principle of separation of concerns. One prompt handles 6 distinct cognitive tasks: record identification, building context assignment, sample interpretation, BAR field mapping, product classification, and risk assessment. This makes debugging, improving, and testing individual capabilities impossible.
[/TABLE]
2.2 Proposed: Multi-Agent Extraction Architecture
Decompose the monolithic extraction into specialised agents within the LangGraph pipeline. Each agent has a focused role, its own prompt template, and can be independently tested, improved, and swapped.
[TABLE]
Agent | Role | Input | Output | Model | Testable?
TableExtractor | Raw row extraction from content | Building content + Docling tables | List of raw row dicts | Claude Sonnet 4 | Yes — count rows vs ground truth
RecordInterpreter | Map raw rows to BAR field semantics | Raw row dicts + BAR schema | Typed ACMExtractionRecord[] | Claude Sonnet 4 | Yes — field accuracy per record
SampleAnalyser | Interpret sample results, friability, condition | Record + sample columns | Enriched sample fields | Claude Sonnet 4 or regex | Yes — enum validation
ProductClassifier | Assign ACM product group/type taxonomy | Product description | acm_product_group, acm_product_type | Regex → LLM fallback | Yes — taxonomy accuracy
QualityValidator | Validate, correct, deduplicate | All records | Clean record set | Rules + LLM correction | Yes — before/after record counts
RecoveryAgent | Find records LLM missed (No Access, sparse) | full_text + existing records | Recovered records | Regex + LLM | Yes — recall measurement
[/TABLE]
2.3 Agent Communication Pattern
Agents communicate through the LangGraph state object — no direct inter-agent messaging. The orchestrator remains the coordinator, dispatching to agents in sequence per building. This is a pipeline-of-agents pattern, not a swarm.
Recommended pattern: Orchestrator dispatches to TableExtractor per building (parallel, semaphore=3). Each building’s raw rows then flow sequentially through RecordInterpreter → SampleAnalyser → ProductClassifier. All buildings’ results merge, then flow through QualityValidator → RecoveryAgent.
[TABLE]
 | SPRINT SCOPING RECOMMENDATIONFor the 1–2 sprint window: implement TableExtractor and RecordInterpreter as the first two agents. Keep SampleAnalyser and ProductClassifier as post-extraction enrichment (they can remain in the current prompt initially). QualityValidator is already effectively built (validation + correction loops). This gives you the highest-value decomposition without rewriting everything.
[/TABLE]
2.4 Pre-Extraction Intelligence: Kill or Fix?
All 4 Stage -1 LLM calls (Structure, Inventory, Page Tagging, Metadata) fail structured output and fall back to heuristics. The heuristics work for production. Two options:
[TABLE]
Option | Effort | Benefit | Recommendation
A: Kill dead LLM calls | Low (1–2 days) | Save ~43s per extraction, simplify code, remove confusion | DO THIS IN SPRINT 1
B: Fix structured output | Medium (3–5 days) | Better accuracy on complex multi-building docs | DEFER to Sprint 3+
[/TABLE]
The completionState envelope issue (OpenRouter wrapping) is the root cause. Fixing it requires either switching to direct Anthropic API calls or adding robust unwrapping. For now, the heuristics are sufficient and battle-tested.
3. Data Model & Export Audit
3.1 Schema Assessment
The SurrealDB schema is well-designed for the core use case. The acm_record table covers all 47 BAR columns plus internal metadata (extraction_confidence, page_number, source_id). SCHEMAFULL enforcement is correct for compliance data.
[TABLE]
 | STRENGTHSurrealDB serving triple duty (document store, vector search, graph) is architecturally elegant and eliminates operational complexity of managing 3 separate databases. This is a good fit for the data volume (2000+ documents, ~50K records estimated).
[/TABLE]
3.2 Export Flexibility Gaps
The architecture mentions per-building, per-site, and consolidated exports but doesn’t detail the export API design. For compliance officers, export is the final deliverable — it deserves first-class treatment.
[TABLE]
Export Type | Current Status | Gap | Priority
Per-building BAR Excel | Built | Works but column ordering needs verification against template | P1
Per-site consolidated | Partially built | Needs site_config merge logic for multi-building sites | P1
Filtered export (by risk, by status) | Not built | Officers need to export subsets (e.g., all high-risk ACM) | P2
CSV export for data interchange | Not built | Useful for integration with other government systems | P3
Audit trail export | Not built | Extraction metadata, confidence scores, corrections applied | P2
[/TABLE]
3.3 Data Model Recommendations
Add an extraction_run table to track pipeline executions (timestamp, model used, accuracy score, records extracted). This enables audit trail and regression detection.
Add an export_template table to store BAR template configuration (column order, headers, formatting rules). Decouple template logic from code.
Consider adding a correction_log table to track every LLM correction applied — this is valuable for improving prompts and measuring correction patterns.
The site_config table needs a one-to-many relationship with sources (one site has many documents over time). Current schema implies 1:1.

4.2 BMAD Measure Phase: Test Harness Blueprint
BMAD V6 requires a Measure phase before any restructure ships. You need an automated benchmark suite that runs on every pipeline change. Here is the blueprint:
4.2.1 Ground Truth Dataset
Minimum 5 benchmark documents: 1 Prensa (Broadmeadows, done), 1 Greencap, 1 Generic, 1 multi-building (5+ buildings), 1 edge-case (sparse tables, No Access heavy).
Each benchmark needs a ground_truth.json with every expected ACMExtractionRecord (all 40+ fields).
Store in a /benchmarks directory with structure: /benchmarks/{doc_name}/source.pdf + ground_truth.json + last_run.json.
4.2.2 Accuracy Metrics
[TABLE]
Metric | Definition | Target | Current
Record Recall | # correct records / # ground truth records | ≥95% | 100% (Broadmeadows only)
Record Precision | # correct records / # extracted records | ≥95% | ~97% (1 extra record)
Field Accuracy | # correct fields / # total fields across records | ≥90% | Not measured
Format Coverage | # formats with ≥90% recall | ≥3 formats | 1 format
Regression Rate | # benchmarks that regressed on latest change | 0 | Not tracked
[/TABLE]
4.2.3 Automated Test Runner
Build a pytest-based test runner that: (1) processes each benchmark PDF through the full pipeline, (2) compares output against ground_truth.json, (3) produces a per-field accuracy report, (4) fails CI if any benchmark drops below threshold. Estimated effort: 3–4 days for the first version.
[TABLE]
 | BMAD GATE: NO RESTRUCTURE WITHOUT BENCHMARKSThe multi-agent restructure MUST be gated behind having at least 3 benchmark documents with ground truth. Without this, you cannot prove the restructure doesn’t regress accuracy. Build the harness first (Sprint 1, Week 1), then restructure (Sprint 1, Week 2 + Sprint 2).
[/TABLE]

6. Multi-Agent Restructure Plan
6.1 Migration Strategy: Incremental, Not Big-Bang
The restructure must be incremental to maintain the 100% Broadmeadows accuracy at every step. Each agent is extracted from the monolithic prompt, tested against benchmarks, and promoted only when accuracy is maintained or improved.
[TABLE]
 | GOLDEN RULENo agent goes live without passing all existing benchmarks at ≥95% recall. The benchmark harness is the safety net. Build it first.
[/TABLE]
6.2 Phase 1: TableExtractor Agent (Sprint 1, Week 2)
Extract the row-identification logic from building_extraction.jinja into a dedicated TableExtractor agent.
Input: Building content (PyMuPDF text + Docling DataFrames)
Output: List of raw row dictionaries (one per ACM record) with original column names preserved
Prompt focus: “Count every row. Same room, different location = separate records. Include No Access entries.”
Test: Row count matches ground truth record count per building
Key benefit: Isolates the #1 accuracy failure mode (missed or merged rows) into a testable unit
6.3 Phase 2: RecordInterpreter Agent (Sprint 2, Week 1)
Takes raw rows from TableExtractor and maps them to typed ACMExtractionRecord objects.
Input: Raw row dicts + BAR schema definition + consultant metadata
Output: ACMExtractionRecord[] with all 40+ fields populated
Prompt focus: “Map these consultant-specific columns to BAR fields. Normalise values to enum sets.”
Test: Per-field accuracy comparison against ground truth
Key benefit: Separates “what are the records” from “what do the fields mean”
6.4 Phase 3: Specialist Enrichment Agents (Sprint 2, Week 2)
SampleAnalyser and ProductClassifier remain as post-extraction enrichment. They can initially stay embedded in RecordInterpreter’s prompt and be extracted later when benchmarks justify the effort.
