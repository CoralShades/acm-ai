01 / Executive Summary

A non-technical overview of what ACM-AI does, why it exists, and how it transforms government compliance workflows.

The Problem

Victorian Government agencies manage thousands of PDF asbestos assessment reports from multiple consulting firms (Prensa, Greencap, and others). Each report must be manually converted into a standardised Building Asbestos Register (BAR) spreadsheet with 47 columns. This process is slow, error-prone, and expensive — costing compliance officers hours per document.

The Solution

ACM-AI automates this conversion using a hybrid approach: computer vision extracts raw tables from PDFs, then AI agents interpret, classify, and normalise the data into BAR-compliant format. The system handles any consultant format without pre-configuration, achieving 100% accuracy on benchmark documents.

How It Works (In Brief)

📄 PDF Upload → 🔍 Table Extraction → 📋 Document Analysis → 🤖 AI Extraction → ✅ Validation → 💾 BAR Output

A compliance officer uploads an asbestos assessment PDF. The system processes the document through two parallel engines — PyMuPDF for reading-order text and Docling for structured table data. An AI pipeline then analyses the document structure, identifies buildings and rooms, extracts every ACM record, validates accuracy, and stores the results. Officers review the data in an interactive spreadsheet before exporting to BAR-compliant Excel.

Frontend

Next.js 15 on Vercel. Server-side rendering with React. AG Grid Enterprise for spreadsheet views, CopilotKit for AI chat, AG-UI protocol for SSE streaming. Connects to backend via Cloudflare tunnel.

Backend API

FastAPI running locally (no Docker). REST endpoints for CRUD, SSE endpoints for live extraction progress. Manages the command queue and coordinates with the background worker process.

Worker Process

surreal-commands-worker polls the SurrealDB command table for pending jobs. Claims a command, runs the LangGraph extraction pipeline, updates status on completion. Handles both source processing and ACM extraction commands.

Database

SurrealDB v2 in Docker. Serves triple duty: document/record storage (SCHEMAFULL tables), vector search (MTREE index with cosine similarity), and knowledge graph (RELATION tables with traversal syntax).

GPU Processing

RTX 4090 accelerates Docling's TableFormer model (ACCURATE mode) for table structure recognition. Also powers local Ollama models for embedding generation. Critical for production throughput on 2000+ documents.

AI Routing

OpenRouter provides multi-provider access with automatic fallback. Primary: Anthropic (Claude Sonnet 4). Provider preferences exclude Amazon Bedrock and Azure, prioritise Anthropic → Google → OpenAI.

06 / Phase 1: Source Processing

The dual-engine PDF extraction that runs before any AI involvement — converting raw PDFs into machine-readable content.

Why Two Extraction Engines?

No single PDF extraction tool captures everything. PyMuPDF excels at reading-order text and page coverage (including sparse text sections), while Docling's TableFormer excels at structured table extraction with row coherence. Together they achieve what neither can alone.

PyMuPDF Output

Full document text with --- Page N --- markers. Captures all pages including sparse text areas that Docling's table detector misses (e.g., "No Access" entries on continuation pages). Stored as source.full_text.

Docling Output

Per-table DataFrames with row-coherent data. Each register table becomes a separate acm_table_section row with markdown, HTML, CSV, and page number. Uses GPU-accelerated TableFormer in ACCURATE mode (~22s per document).

Design Decision: Non-Blocking Docling

Docling runs AFTER PyMuPDF completes. If Docling fails, the pipeline continues with PyMuPDF text only — zero regression risk. This was validated empirically: PyMuPDF alone achieves 28/31, while the hybrid achieves 31/31.

09 / Phase 4: AI Extraction

What the AI model actually does with the assembled context — transforming raw content into structured BAR-compliant records.

The AI's Job: Interpretation, Not Just Extraction

The raw tables are already extracted by Docling. The AI's role is to interpret, normalise, and map the raw data into the 47-column BAR schema. This includes:

🔍 Record Identification

Each row in the register table becomes an ACMExtractionRecord. The AI must correctly count rows, handle merged cells, and recognise that same-room-different-location entries are separate records.

🏗️ Building Context

The AI assigns building_id, building_name, area_type (Interior/Exterior) to each record based on the building context provided by the orchestrator.

🧪 Sample Interpretation

Raw sample results like "ACM Detected", "NAD", "Not Sampled", "As Per [ref]" are normalised into BAR-compliant values: result, friable, material_condition, sample_result.

📊 BAR Field Mapping

Consultant-specific column names (which vary between Prensa, Greencap, etc.) are mapped to standardised BAR fields. The AI handles this dynamically without per-consultant configuration.

🏷️ Product Classification

ACM products are classified into the Victorian BAR taxonomy (T1-T8 Non-friable, T1-T6 Friable). Uses pattern-based regex for common types, LLM fallback for ambiguous items.

⚠️ Risk Assessment

The AI derives risk status from material condition + disturbance potential. Also captures hygienist_recommendations and additional_comments from the assessment narrative.

Output Schema: ACMExtractionRecord (40+ Fields)

The Three Fixes That Achieved 100%

The journey from 28/31 (90.3%) to 31/31 (100%) came from three targeted fixes in the post-extraction pipeline:

Fix 1: Dedup Key Enhancement

Added location to the deduplication key (was: room + product). Previously, two records in the Switch Room with different locations (Switchboard vs Battery Charger) were merged as duplicates. Result: 31→30 after dedup (was 31→28).

Fix 2: Prompt Engineering

Added "CRITICAL: Structured Table Extraction Rules" to the prompt with explicit instructions to count rows, preserve same-room-different-location entries, and extract "No Access" entries. Recovered Record #9 (Battery Charger) and #30 (Lift Foyer).

Fix 3: Regex Recovery Fallback

New _recover_no_access_records() function runs post-dedup and scans full_text for "No Access" entries the LLM missed. Recovered Record #31 (Disabled Toilet) which was on page 8 — a sparse text area below Docling's table detection threshold.

11 / Phase 6: Storage & Export

How validated records are persisted, enriched with embeddings, linked in the knowledge graph, and exported to BAR format.

💾 SurrealDB Persistence

Each record is stored in the acm_record SCHEMAFULL table with all 40+ fields. Parent acm_table_section records link records to their source tables. Cascade delete ensures records are removed when a source is deleted.

🧮 Vector Embeddings

Enriched text (Building|Room|Page|fields) is embedded via Ollama (Qwen 2.5:7b) and stored as 1024-dimension vectors with MTREE cosine index. Enables semantic search like "asbestos in the kitchen".

🕸️ Knowledge Graph

SurrealDB RELATION tables link school→building→room→acm_record with graph traversal. Enables queries like "show all ACM in Building A" and powers the React Flow visualisation.

📊 BAR Export

Records export to Excel using the Victorian BAR template (47 columns). Site configuration fields (Department, Agency, Building Type) are merged from the site_config table. Supports per-building, per-site, and consolidated exports.

Key Lesson

Model switching alone doesn't solve extraction problems. Most accuracy issues stemmed from PDF structural challenges (merged cells, sparse text sections, row deduplication) rather than model limitations. The breakthrough came from combining better PDF tooling (Docling DataFrames) with targeted post-processing (dedup key fix, regex recovery).

17 / Design Principles

The architectural principles that guide every decision in ACM-AI.

1. Unified Pipeline

Every document — regardless of format, consultant, or building count — flows through the same orchestrated pipeline. No special-case routing. The system adapts to the document, not the other way around.

2. Hybrid Extraction

Combine complementary tools (PyMuPDF + Docling) rather than relying on a single engine. Each tool covers the other's blind spots. Non-blocking design means failures in one engine don't affect the other.

3. AI Interprets, Rules Validate

AI handles the fuzzy work (interpretation, normalisation, classification). Deterministic rules handle the precise work (validation, deduplication, schema enforcement). Never trust AI output without Pydantic validation.

4. Graceful Degradation

Every AI call has a non-AI fallback. Structured output fails? JSON parser. LLM misses a record? Regex recovery. Building inventory fails? Legacy extraction. The system always produces output.

5. Measure Before Fixing

Every change is validated against ground-truth benchmarks (Broadmeadows 31 records, Alexander 43 records). No fix ships without empirical measurement. Research spikes precede implementation.

6. Design for the Officer

End users are compliance officers, not developers. The interface uses familiar mental models (jobs, spreadsheets, exports). Technical sophistication is hidden behind a simple two-step workflow: upload, then extract.
