ACM-AI Solution Architecture

An AI-powered platform that extracts Buildings and ACM Items from thousands of consultant PDF reports, mapping them precisely to VAEA's Salesforce Building__c and Item__c object model — eliminating manual data entry from PDF tables.

Salesforce Objects Building__c → Item__c
Building Fields 143 (29 extractable)
Item/ACM Fields 154 (35 extractable)
AI Provider Anthropic Claude Sonnet
Version March 2026

01 / Problem Statement

The core challenge VAEA faces and why AI-powered extraction is the solution.

The Problem

VAEA manages thousands of PDF asbestos assessment reports from multiple consulting firms (Prensa, Greencap, and others). Each PDF contains tables listing Buildings and ACM (Asbestos Containing Material) items found within those buildings. Officers must manually read these tables and enter every Building and every ACM item into Salesforce's Building__c and Item__c objects — field by field, picklist by picklist. A single PDF can contain multiple buildings and dozens of ACM items. At scale, this is unsustainable.

Manual Data Entry at Scale

Each PDF report requires reading tables, identifying buildings and rooms, then manually populating 29+ building fields and 35+ ACM item fields per record in Salesforce.

Variable PDF Formats

Reports come from different consulting firms (Prensa, Greencap, generic) with different table layouts, column names, and structures. No single template fits all.

Complex Object Model

Salesforce's Building__c has 143 fields with dependent picklists (e.g., Building Type → Asset Category). Item__c has 154 fields with dependent picklists (e.g., Friability → ACM Product Group). AI must respect these dependencies.

One Building → Many ACMs

A single building can have dozens of ACM items across different rooms and locations. A single PDF can contain multiple buildings, each with their own set of ACMs.

The Solution

ACM-AI uses a multi-stage AI extraction pipeline powered by Anthropic Claude Sonnet to read PDF tables, identify buildings and ACM items, extract field values, validate against Salesforce picklist values, and output structured data matching the exact Building__c and Item__c schemas — ready for officer review and export.

Key Relationship

Item__c.Building_Code__c is a Master-Detail relationship to Building__c. Every ACM item must belong to exactly one Building. When a Building is deleted, all its Items cascade-delete. The AI pipeline must correctly group extracted ACM items to their parent Building.

Building__c Record Types

Building (default) — the record type we extract to.
Also available: Structure, Vehicle, Master — not in scope for PDF extraction.

Item__c Record Types

ACM (default) — the record type we extract to.
Also available: PCB, Lead Containing Paint, Crystalline Silica, Biological Hazards, Ozone Depleting Substances, Space/Area — not in scope.

Why This Matters for AI Extraction

The AI cannot simply extract values in isolation. If it extracts Friability = "Non Friable", then ACM Product Group must be one of the non-friable groups (e.g., "Cement products" not "Cement products (f)"). If it extracts ACM Product Group = "Insulation Products", then Item Name must be a value valid for insulation (e.g., "Pipe lagging" not "Floor tiles"). The validation layer enforces these chains.

Phase 1 / PDF Processing

Two complementary engines run in parallel on each uploaded PDF.

PyMuPDF — Text Extraction

Extracts reading-order text from every page. Provides the raw text context that the AI uses for building identification, metadata extraction, and understanding document structure.

Docling + TableFormer — Table Extraction

GPU-accelerated (CUDA) table detection and recognition. Identifies table boundaries, cell contents, and column headers. This is critical because the ACM data lives in tables — the AI needs structured table data to extract individual ACM records accurately.

Phase 2 / Structure Analysis

Three Claude Sonnet calls analyse the document before extraction begins.

Document Structure

Identifies the document type (Division 5, Risk Assessment, Audit), sections, and table of contents. Determines how many buildings are in the document.

Building Inventory

Lists every building found in the document with page ranges. Each building gets a processing plan. This is critical for PDFs with multiple buildings — each building's data must be extracted and grouped separately.

Page Tagging

Tags each page by content type (cover, table of contents, building info, ACM table, appendix). This tells the extraction phase which pages to focus on for each building.

Phase 3 / AI Extraction

The core extraction phase — Claude Sonnet extracts Buildings and ACMs from the identified tables.

Per-Building Extraction

For each building identified in Phase 2, the orchestrator sends the relevant pages and table data to Claude Sonnet with two extraction tasks:

Extract Building Fields → Building__c

Extracts: Building Name, Address, Suburb, Postcode, Construction Type, Year Built, Number of Levels, Date of Inspection, Roof Type, Estimated Size. These map directly to Building__c fields.

Extract ACM Items → Item__c

For every row in the ACM tables, extracts: Item Name, Friability, ACM Product Group, ACM Product Type, Condition, Disturbance Potential, Room/Area, Floor Level, Location, Sample Result, Sample Number, Quantity, Assessor, Recommendations. Each maps to an Item__c field with the correct picklist value.

Phase 4 / Validation & Correction

Every extracted record is validated against the Salesforce schema before storage.

Pydantic Schema Validation

Type checking, required field validation, and format coercion (dates, numbers). Uses Pydantic v2 models that mirror the Salesforce field types.

Picklist Value Validation

Every picklist value is checked against the exact Salesforce picklist values loaded from the schema config. If AI returns "Good" for Condition but Salesforce only accepts "Poor|Fair|Stable|Unknown|N/A", it's flagged.

Dependency Chain Validation

Verifies that dependent picklist values are valid for their controller. If Friability = "Non Friable", ACM Product Group cannot be "Insulation products (f)" (which is friable-only).

AI Correction Loop

Invalid fields are sent back to Claude Sonnet with the specific error and valid options. The AI returns corrected values. Max 3 correction attempts per record before flagging for manual review.

Business Rule: Negative Result Clears Fields

When Sample_Result__c = "Negative", the system automatically sets Condition__c = "N/A (negative)" and Disturbance_Potential__c = "N/A". This mirrors the Salesforce business rule where negative results don't require condition or disturbance assessment.

Phase 5 / Review & Export

Officers review and correct extracted data before export.

AG Grid Spreadsheet Review

All extracted records displayed in an interactive AG Grid spreadsheet. Officers can edit cells, filter by building, sort by condition/risk, and correct any AI errors. Column definitions and picklist dropdowns are driven by the field schema config.

Salesforce-Ready Export

Export to Excel/CSV with exact Salesforce API field names as column headers. Separate sheets for Building__c and Item__c records. Picklist values exactly match Salesforce. Ready for Salesforce Data Loader or Data Import Wizard.

Site Configuration Merge

Officer-configured fields (Department, Organisation, Building Type, Asset Category, Owned/Leased) are merged into the export. These fields cannot be extracted from PDFs — they come from the site config set up before extraction.

12 / Design Principles

Architectural decisions that guide the system.

1. Salesforce Schema Drives Everything

The Salesforce Building__c and Item__c schemas are the source of truth. Picklist values, dependent fields, and field types are loaded from schema config and used to drive AI prompts, validation, grid columns, and export formats.

2. Hybrid PDF Extraction

PyMuPDF for text + Docling for tables. Each covers the other's blind spots. Non-blocking design means one engine failing doesn't stop the other.

3. AI Extracts, Rules Validate

Claude Sonnet handles the fuzzy work (interpretation, normalisation). Pydantic and picklist rules handle the precise work (validation, dependency enforcement). Never trust AI output without schema validation.

4. Per-Building Extraction

Every building is extracted independently. This ensures correct Building → ACM Item grouping and handles PDFs with 1 building or 20 buildings identically.

5. Graceful Degradation

Every AI call has a fallback. Structured output fails? JSON parser. LLM misses a record? Regex recovery. Validation fails? AI correction loop. The system always produces output.

6. Design for the Officer

End users are compliance officers, not developers. The workflow is simple: upload PDF → review extracted data in spreadsheet → export. All complexity is hidden behind the pipeline.
